# AssignmentHub 개발 지시 프롬프트

현재 작업 폴더를 확인하고, 아래 요구사항에 따라 **AssignmentHub: 로컬 과제 제출·관리 서버**를 구현해 주세요. GitHub 저장소 이름은 `assignment-hub`를 사용하려고 합니다. 이 문서가 개발의 기준입니다.

설계 설명에 그치지 말고 실행 가능한 코드, 실행 도구, 설정 예제, 사용자 등록용 엑셀 템플릿, 운영 문서, 의미 있는 테스트까지 완성해 주세요. 기존 저장소라면 먼저 `AGENTS.md`, 코드, 의존성, 작업 중인 변경 사항을 확인하고 기존 작업을 보존하세요. 외부 저장소 생성이나 배포가 필요한 작업은 이 요청에 포함하지 않습니다.

## 1. 목표와 기본 가정

운영자의 로컬 PC에서 서버를 실행하고, 사전에 등록된 수강생이 웹브라우저로 접속해 과제 파일을 제출하는 도구를 만듭니다. 한 PC에서 교육과정 또는 차수별 서버 인스턴스를 여러 개 실행할 수 있어야 합니다. 모든 계정 정보와 제출 파일은 운영자 PC에 저장합니다.

아직 확정되지 않은 사항은 다음 기본값으로 구현하고 설정으로 변경할 수 있게 해 주세요. 이 기본값은 확정된 운영 정책이 아니라 개발을 진행하기 위한 가정입니다.

| 항목 | 기본값 또는 범위 |
|---|---|
| 우선 지원 환경 | Windows 10/11, 64비트 Python. 핵심 로직은 다른 OS에서도 테스트 가능하게 분리 |
| 접속 범위 | 서버 PC에 접근 가능한 교육장·사내 네트워크 |
| 사용자 환경 | PC의 Chrome 또는 Edge 웹브라우저 |
| 사용자 화면 | 한국어 |
| 파일당 최대 크기 | **2GiB = 2,147,483,648바이트**. 사용자가 언급한 ‘2G’를 이 값으로 가정 |
| 사용자별 누적 한도 | 인스턴스당 10GiB. 보존 중인 모든 과제·재제출 버전을 합산 |
| 디스크 최소 여유 공간 | 5GiB |
| 한 번의 제출에 포함할 파일 | 최대 10개. 사용자가 명시적으로 선택한 파일들을 한 제출 묶음으로 처리 |
| 전송 청크 크기 | 기본 8MiB |
| 동시 파일 업로드 | 인스턴스당 기본 4개. 나머지는 대기 또는 재시도 가능한 상태로 안내 |
| 미완료 업로드 보관 시간 | 마지막 활동 후 24시간. 설정 가능 |
| 과제 운영 | 인스턴스에 기본 과제 1개를 생성하고, 관리자가 과제를 추가·수정·접수 종료 가능 |
| 제출 대상 | 해당 인스턴스의 활성 수강생 전원. 관리자 계정은 제출 대상에서 제외 |
| 재제출 | 허용. 이전 제출물을 보존하고 새 제출번호 부여 |
| 삭제 정책 | 완료된 제출물은 자동 삭제하지 않음. 사용자 삭제 기능은 초기 범위에서 제외 |

화면에는 GB와 GiB를 혼용하지 말고, 용량 표시 단위와 바이트 기준을 일치시켜 주세요. 실제 인원과 동시 접속 규모는 미정이며 부하 테스트 설정으로 바꿀 수 있어야 합니다.

## 2. 기술 구성과 실행 구조

다음 구성을 기본으로 구현하세요.

- **Streamlit:** 로그인, 비밀번호 변경, 과제 선택, 제출 이력, 관리자 화면.
- **FastAPI 기반 서버:** 계정 인증·권한 검사, 업로드 세션, 청크 수신, 제출 확정, 파일 다운로드.
- **SQLite:** 인스턴스별 계정, 과제, 제출 내역, 업로드 상태, 용량 예약, 관리 작업 기록.
- **로컬 파일시스템:** 업로드 중인 임시 파일과 완료된 제출 파일.
- **브라우저 업로더:** Streamlit 화면에 연결된 컴포넌트 또는 같은 접속 주소 아래의 업로드 페이지. 파일은 브라우저에서 업로드 API로 직접 전송.
- **실행 도구:** 인스턴스별 설정을 읽고 필요한 프로세스를 함께 시작·중지.

대용량 과제 파일을 `st.file_uploader`로 먼저 받은 뒤 FastAPI에 전달하는 방식은 사용하지 마세요. 전체 파일을 Python `bytes`, `BytesIO`, 세션 상태, 캐시, Base64, 브라우저의 단일 `ArrayBuffer`에 올리지 마세요. 작은 명단 엑셀을 읽는 기능과 대용량 과제 전송 경로는 구분하세요.

FastAPI를 쓴다는 사실만으로 대용량 처리가 해결된 것으로 간주하지 마세요. 요청 본문을 제한된 크기로 읽고 디스크에 기록해야 하며, 프록시·미들웨어·해시 계산·최종 파일 조립·다운로드에도 전체 파일 버퍼링이 없어야 합니다. 파일 I/O가 이벤트 루프를 장시간 막지 않도록 처리하세요.

운영자가 지정하는 **사용자 접속 포트는 인스턴스당 하나**로 구성하세요. HTTP와 WebSocket을 지원하는 프록시 또는 게이트웨이로 Streamlit 화면과 API를 같은 origin 아래에 연결하고, 내부 포트는 실행 도구가 충돌 없이 관리하게 하세요. 내부 서비스는 loopback에 바인딩하세요. 검증된 프록시 구성을 선택하고 운영자의 수동 설정을 최소화하세요. Streamlit을 일반 ASGI 앱처럼 직접 mount할 수 있다고 가정하지 마세요.

WebSocket 연결, 큰 파일 전송, 재시도, 인증이 이 단일 접속 주소를 통해 실제로 동작해야 합니다. 필요 구성요소는 설치·실행 도구에서 관리하고, 일상적인 실행에 개발용 프런트엔드 서버나 CDN 접속을 요구하지 마세요.

계정·용량·제출 상태의 변경은 API 계층에서 일관되게 처리하세요. DB 트랜잭션은 짧게 유지하고 파일 전송 전체 시간 동안 쓰기 잠금을 잡지 마세요. Streamlit의 사용자 인증 상태를 프로세스 전역 변수나 모든 사용자에게 공유되는 캐시에 보관하지 마세요.

## 3. 인스턴스 생성과 서버 관리

운영자는 인스턴스 생성 시 다음을 설정할 수 있어야 합니다.

- 고유한 `instance_id`와 화면에 표시할 과정명.
- 접속 포트와 바인딩 주소.
- 사용자에게 안내할 서버 IP 또는 호스트명.
- 로컬 저장 루트 폴더.
- 파일당 제한, 사용자별 누적 한도, 디스크 최소 여유 공간.

실행 전 포트 충돌, 저장 폴더 쓰기 권한, 설정 오류, 디스크 공간, 동일 인스턴스 중복 실행을 검사하세요. 같은 저장 루트를 다른 인스턴스가 동시에 사용하지 못하도록 정규화한 경로와 실행 잠금을 관리하세요.

인스턴스마다 설정, DB, 제출물, 임시 파일, 로그, 인증 비밀값을 독립적으로 관리하세요. 하나의 인스턴스를 종료해도 다른 인스턴스는 계속 실행되어야 합니다. 재시작 후 계정과 제출 기록을 복원하고, 진행 중이던 업로드는 복구 정책에 따라 처리하세요.

실행 도구에서 생성·시작·상태 확인·중지 기능과 접속 URL을 제공하세요. 프로세스 시작 실패 시 그 실행에서 생성한 프로세스만 정리하고, PC의 다른 Python·Streamlit 프로세스를 일괄 종료하지 마세요.

예를 들어 하나의 PC에서 다음 두 인스턴스를 운영할 수 있어야 합니다.

| instance_id | 외부 접속 포트 | 저장 루트 예시 |
|---|---:|---|
| course_01 | 8501 | `D:\Assignments\course_01` |
| course_02 | 8502 | `D:\Assignments\course_02` |

사용자에게는 서버 PC의 네트워크 주소와 지정 포트를 안내하세요. 다른 PC의 사용자가 `localhost`로 접속하도록 안내하지 마세요. 네트워크 인터페이스가 여러 개면 안내 주소를 운영자가 선택·수정할 수 있게 하세요.

## 4. 사용자 명단과 계정 등록

관리자 화면에서 `.xlsx` 명단을 등록할 수 있어야 합니다. 템플릿에는 다음 컬럼을 사용하세요.

| 컬럼 | 필수 여부 | 의미 |
|---|---|---|
| user_id | 필수 | 로그인 ID. 텍스트로 입력하며 앞자리 0을 보존 |
| name | 필수 | 화면에 표시할 이름 |
| group | 선택 | 반, 부서 또는 분반 구분 |

임의 회원가입은 제공하지 않습니다. 계정은 관리자만 생성할 수 있게 하세요.

명단 반영 전 미리보기와 검증 결과를 보여 주세요. 필수 컬럼 누락, 빈 ID, 파일 내 중복 ID, 기존 계정과의 중복을 명확히 표시하세요. 오류가 있는 행을 조용히 누락하거나 숫자형 ID에서 잃어버린 앞자리 0을 임의로 추정하지 마세요. 템플릿의 ID 열은 텍스트 서식으로 만드세요.

초기 정책은 ID의 앞뒤 공백 제거 후 대소문자를 구분하는 것으로 문서화하세요. 표시 ID와 내부 저장용 식별자는 분리하고, ID를 그대로 파일 경로로 사용하지 마세요.

새 명단을 다시 반영할 때는 새 계정만 추가하고 기존 계정의 이름·그룹 변경은 확인 가능한 방식으로 적용하세요. 기존 비밀번호, 제출 기록, 계정 활성 상태는 명시적 관리 작업 없이 바꾸지 마세요. 재등록을 비밀번호 초기화로 처리하지 마세요.

등록된 사용자별로 서로 다른 임시비밀번호를 발급하세요. 관리자가 배포할 수 있는 일회성 결과 화면 또는 다운로드 기능을 제공하되 평문 비밀번호를 일반 로그나 운영 DB에 저장하지 마세요. 실사용 명단과 임시비밀번호 출력 파일은 Git 추적 대상에서 제외하세요. 명단에는 수강생만 등록하고 관리자 권한은 로컬 초기 설정 등 별도 관리 절차에서 부여하세요.

## 5. 로그인과 비밀번호 변경·초기화

사용자 흐름은 다음 순서입니다.

1. 사용자가 해당 인스턴스의 접속 URL을 엽니다.
2. ID와 임시비밀번호로 본인 계정을 확인합니다.
3. 최초 접속 또는 관리자 초기화 상태이면 새 비밀번호와 확인 입력을 받습니다.
4. 비밀번호 변경을 완료한 뒤 새 비밀번호로 정상 로그인합니다.
5. 과제 제출 화면을 사용할 수 있습니다.

비밀번호 변경 전에는 과제 조회·업로드·다운로드 권한을 부여하지 마세요. 이 제한은 Streamlit 화면뿐 아니라 API에서도 검사해야 합니다.

비밀번호는 Argon2id 등 검증된 비밀번호 해시 라이브러리로 저장하세요. 직접 만든 암호화나 단순 SHA-256 해시로 비밀번호를 저장하지 마세요. 기본 비밀번호 정책은 최소 12자, 최대 128자로 두고 문서화하세요. 붙여넣기를 허용하고 기존·임시비밀번호와 동일한 값으로 변경하지 못하게 하세요.

관리자는 사용자별 비밀번호 초기화를 할 수 있어야 합니다. 초기화하면 새 임시비밀번호를 발급하고 `must_change_password` 상태를 설정하며, 기존 로그인 세션과 업로드 권한을 즉시 무효화하세요. 다시 인증하고 비밀번호를 바꾸기 전에는 이전 토큰으로 청크 업로드나 제출 확정을 계속할 수 없어야 합니다.

계정 비활성화, 로그아웃, 세션 만료도 서버가 강제하세요. 로그인 반복 실패에 대한 속도 제한을 두고, 비밀번호·세션 토큰·일회성 권한 토큰을 로그나 URL에 남기지 마세요.

Streamlit 로그인 상태와 브라우저 업로더 사이에 인증을 안전하게 연결하세요. 예를 들어 서버가 사용자·인스턴스·업로드 작업에 한정된 짧은 수명의 권한을 발급할 수 있습니다. 프런트엔드가 보내는 `user_id`나 숨겨진 입력값을 신뢰해 저장 대상을 결정하지 마세요. 모든 API 요청에서 서버가 사용자와 작업 소유권을 확인하세요.

서로 다른 포트만으로 브라우저 쿠키가 분리된다고 가정하지 마세요. 인스턴스별 쿠키 이름, 비밀값, 세션 저장소를 분리하고, 토큰·세션에 인스턴스 범위를 검증하세요. 두 인스턴스에 같은 ID가 있어도 로그인과 비밀번호 변경이 서로 영향을 주면 안 됩니다.

관리자 최초 계정은 서버 PC의 초기 설정에서 생성하세요. 기본 관리자 비밀번호를 하드코딩하거나 네트워크의 첫 방문자가 관리자가 되게 하지 마세요. 관리자는 전체 제출물 접근과 계정 초기화 권한을 갖고, 일반 사용자는 본인의 제출물에만 접근할 수 있어야 합니다.

## 6. 과제와 제출 동작

관리자에게 과제명, 설명, 접수 중·종료 상태를 관리하는 화면을 제공하세요. 초기 인스턴스에는 기본 과제를 하나 만들어 바로 제출을 받을 수 있게 하세요.

사용자는 접수 중인 과제를 선택하고 하나 이상의 파일을 업로드합니다. 파일을 선택한 것만으로 전송하지 말고, 명시적인 제출 시작 동작을 제공하세요. 업로드 전 파일명, 각 파일의 크기, 합계, 적용되는 용량 제한을 보여 주세요.

한 번의 제출은 고정된 파일 목록을 가진 하나의 묶음입니다. 묶음의 모든 파일이 검증·저장되고 제출 DB 기록이 확정된 경우에만 제출 완료로 표시하세요. 일부 파일만 전송된 묶음은 미완료이며 관리자 제출자 집계에도 포함하지 마세요. 진행 중인 묶음에서 파일을 임의로 누락시켜 완료 처리하지 마세요.

재제출은 새 제출번호를 부여해 보관하세요. 동일 파일명을 덮어쓰지 말고, 가장 최근에 완료된 제출을 기본으로 표시하면서 이전 완료 이력을 볼 수 있게 하세요. 새 제출이 실패해도 이전 완료 제출은 유지되어야 합니다.

접수 종료는 신규 제출 시작을 막고, 종료 전에 시작된 유효한 업로드는 보관 시간 내에 완료할 수 있게 하는 것을 기본 정책으로 하세요. 계정 초기화·비활성화에 따른 권한 무효화는 이 정책과 별개로 즉시 적용하세요.

제출 완료 화면에는 제출번호, 과제명, 사용자 ID, 원본 파일명, 파일별 크기, 서버 기준 제출 완료 시각을 표시하세요. 시각은 UTC로 저장하고 화면과 내보내기에는 설정된 시간대를 명시하세요. 기본 표시 시간대는 `Asia/Seoul`입니다.

## 7. 대용량 업로드, 진행률, 실패와 재시도

단일 파일 2GiB를 지원하고, 여러 사용자가 큰 파일을 동시에 제출해도 파일 크기에 비례해 서버 메모리가 계속 증가하지 않도록 구현하세요.

브라우저에서 `File.slice()` 등으로 파일을 제한된 크기로 나누어 전송하고, 서버는 인증된 업로드 세션에 연결된 임시 파일에 순차 기록하세요. 초기 구현은 파일별 순차 청크 전송으로 단순화하고 여러 사용자·파일 사이의 동시성을 관리하세요.

청크를 받을 때 업로드 소유권, 허용된 상태, 예상 offset 또는 순서, 청크 크기, 누적 크기를 검사하세요. `Content-Length`나 클라이언트가 신고한 파일 크기만으로 제한을 판단하지 말고 실제 수신 바이트도 검증하세요. 연결 종료나 청크 중간 오류가 나면 마지막 확정 offset에서 안전하게 재개할 수 있어야 합니다.

진행 화면에는 다음을 표시하세요.

- 현재 파일명과 전체 파일 개수 중 순번.
- 파일별 전송량 / 전체 크기와 진행률.
- 제출 묶음의 전체 전송량과 진행률.
- 대기 중, 전송 중, 연결 끊김, 재시도 중, 검증 중, 저장 중, 제출 완료 상태.
- 실패 사유, 재시도 가능 여부, 재시도·취소 동작.

진행률은 실제 전송 이벤트와 서버가 인정한 수신량을 기반으로 계산하세요. 일정 시간마다 임의로 숫자를 증가시키는 가짜 진행률을 사용하지 마세요. 전송량이 100%가 되어도 검증과 저장이 남아 있으면 해당 상태를 계속 표시하고 성공 메시지는 보류하세요.

일시적 연결 장애에는 횟수가 제한된 자동 재시도와 수동 재시도를 제공하세요. 전송 상태 조회 API로 서버가 보관한 offset을 확인해 이어 올리세요. 동일 청크나 제출 확정 요청을 재전송해도 중복 파일·중복 제출 기록·중복 용량 차감이 발생하지 않도록 멱등성을 보장하세요.

업로드 세션, 파일 목록, 확정 offset, 예약 용량을 영속 저장하세요. 브라우저 새로고침 또는 서버 재시작 후 다시 로그인하면 유효한 미완료 작업을 조회할 수 있어야 합니다. 브라우저의 파일 접근 권한이 사라진 경우 같은 파일을 다시 선택하도록 안내하고, 크기와 파일명뿐 아니라 청크 해시 등으로 잘못된 파일을 이어 붙이지 않도록 검증하세요.

취소하거나 보관 시간이 지난 미완료 업로드는 임시 파일과 용량 예약을 함께 정리하세요. 진행 중인 작업을 정리 작업이 삭제하지 않도록 동시성 처리를 하고, 마지막 활동 시간 기준으로 만료를 판단하세요.

## 8. 제출 완료의 정확성과 장애 복구

파일시스템의 저장과 SQLite 트랜잭션은 하나의 원자적 트랜잭션이 아니라는 점을 전제로 설계하세요. 최소한 `uploading`, `paused`, `verifying`, `finalizing`, `completed`, `failed`, `cancelled`, `expired` 같은 상태를 정의하고 합법적인 상태 전이와 재시도 규칙을 문서화하세요. 명칭은 바꿔도 의미는 유지해야 합니다.

제출 완료 조건은 다음을 모두 만족하는 것입니다.

1. 묶음에 선언된 모든 파일을 빠짐없이 수신함.
2. 파일별 실제 크기와 전송 무결성을 검증함. SHA-256 등 파일 해시를 기록하되 제한된 메모리로 계산함.
3. 임시 파일의 쓰기를 완료하고 flush·동기화 등 선택한 내구성 처리를 수행함.
4. 완료 파일을 최종 저장 위치로 이동함. 임시 파일과 최종 파일은 같은 볼륨에 두고, 가능하면 복사 대신 원자적 이름 변경을 사용함.
5. 파일 경로, 원본 이름, 크기, 해시, 사용자, 과제, 제출번호, 완료 시각과 상태를 DB에 커밋함.
6. 예약 용량을 완료 사용량으로 일관되게 전환함.

이후에만 클라이언트에 `completed`를 반환하세요. 파일 저장 실패나 DB 커밋 실패는 성공으로 응답하면 안 됩니다. 디스크의 파일이 이동됐지만 DB 확정이 안 된 상태, DB 확정 후 응답이 유실된 상태를 각각 복구할 수 있어야 합니다.

재시작 시 미완료 상태, 실제 파일, 마지막 확정 offset을 대조해 재개·재검증·정리할 수 있게 하세요. 확정 전의 파일은 다운로드나 완료 목록에 노출하지 마세요. 완료 응답이 유실된 뒤 같은 요청이 다시 오면 기존 제출 결과를 반환하세요.

제출 성공을 반환한 뒤 서버 프로세스가 재시작되어도 완료 파일과 기록이 함께 남아야 합니다. 지원하는 내구성 범위와 파일이 수동 삭제되는 등 외부 변경 발견 시의 처리도 운영 문서에 적으세요.

## 9. 용량 관리

다음 세 가지를 서로 독립된 제한으로 구현하세요.

| 제한 | 적용 방식 |
|---|---|
| 파일당 최대 크기 | 파일별 제한. 요청 시작과 실제 수신 중 모두 검사 |
| 사용자별 누적 한도 | 인스턴스 내 보존 중인 모든 완료 제출 버전의 합계에 진행 중인 예약 용량을 더해 판단 |
| 디스크 여유 공간 | 실제 저장 볼륨의 사용 가능 용량과 설정한 최소 여유 공간을 기준으로 판단 |

제출 시작 시 파일 목록의 예상 합계만큼 사용자 용량을 예약하고, 같은 사용자가 여러 탭에서 동시에 요청해도 한도를 초과해 예약하지 못하도록 DB 트랜잭션으로 처리하세요. 성공 시 완료 사용량으로 전환하고 취소·실패 정리·만료 시 예약을 해제하세요. 재시도할 때 같은 업로드의 용량을 중복 예약하지 마세요.

실제 디스크 여유 공간을 계산할 때 이미 디스크에 기록한 임시 파일과 아직 기록하지 않은 예약분을 중복 계산하지 마세요. 조립 과정에서 임시 파일과 최종 파일을 함께 보관해야 하는 설계라면 그 추가 공간도 반영하세요.

여러 인스턴스가 같은 물리 디스크를 사용할 수 있습니다. 다른 인스턴스와 외부 프로그램이 공간을 사용하므로 시작 시 확인만으로 디스크 공간을 보장한다고 가정하지 마세요. 전송 중과 최종 저장 전에 재확인하고, 공간 부족 쓰기 오류를 포착해 미완료 상태와 정리 정책을 적용하세요. 해당 업로드 실패가 다른 사용자의 제출물이나 다른 인스턴스의 DB를 손상시키면 안 됩니다.

사용자에게는 본인 사용량·한도·이번 제출 예상 사용량을, 관리자에게는 인스턴스 사용량·진행 중 임시 파일 용량·예약 용량·볼륨 잔여 공간을 구분해 보여 주세요. 용량 부족 오류에서는 어떤 제한에 걸렸는지와 필요한 조치를 안내하세요.

## 10. 관리자 화면과 제출 현황

관리자는 다음을 할 수 있어야 합니다.

- 사용자 명단 등록, 사용자 검색, 계정 활성·비활성화, 비밀번호 초기화.
- 과제 추가·수정, 접수 시작·종료.
- 과제별 대상자 수, 제출자 수, 미제출자 수, 진행·실패 건수 확인.
- 제출자·미제출자 목록을 ID, 이름, 그룹 기준으로 검색·필터링.
- 제출 시각, 제출번호, 제출 버전, 원본 파일 목록, 파일별 크기, 총용량 확인.
- 완료된 파일의 인증된 다운로드와 서버 저장 위치 확인.
- 제출 현황을 CSV 또는 XLSX로 내보내기.
- 적용 중인 용량 설정과 디스크 현황 확인.

제출자는 선택한 과제에 `completed` 상태의 제출이 하나 이상 있는 활성 수강생으로 정의하세요. 재제출 여러 건을 여러 명으로 세지 마세요. 업로드 중·검증 중·실패만 있는 사용자는 완료 제출자로 집계하지 마세요. 비활성 계정의 기존 제출 이력은 보존하고 별도 조회할 수 있게 하세요.

비밀번호 초기화·계정 비활성화·과제 접수 상태 변경 등 관리 작업은 수행한 관리자와 시각을 기록하세요. 비밀번호나 토큰 자체는 기록하지 마세요.

일반 사용자는 본인의 제출 내역과 완료 파일만 조회·다운로드할 수 있어야 합니다. 직접 API를 호출하거나 URL의 식별자를 바꾸는 경우에도 같은 권한 검사를 적용하세요. 2GiB 파일 다운로드도 메모리에 통째로 올리지 말고 스트리밍 처리하세요.

## 11. 저장 구조와 기본 보호

저장 루트에는 인스턴스 식별 정보와 함께 DB, 완료 파일, 임시 파일, 로그를 구분해 보관하세요. 완료 파일은 과제·사용자·제출번호로 추적할 수 있어야 합니다. 실제 경로에는 서버가 생성한 안전한 식별자를 사용하고 원본 파일명은 메타데이터로 보존하세요.

- `..`, 절대경로, 경로 구분자, Windows 예약 이름, ADS 표기, 지나치게 긴 이름, 한글·공백·중복 파일명을 안전하게 처리하세요.
- 업로드 파일을 자동 실행하거나 압축 해제하지 마세요. 기본은 파일 보관 기능입니다.
- 제출 폴더를 인증 없는 정적 웹 경로로 공개하지 마세요. 다운로드는 권한을 확인한 뒤 첨부파일로 제공하세요.
- 파일명과 사용자 입력을 화면에 표시할 때 이스케이프하고, CSV/XLSX 내보내기에는 수식 주입을 방지하세요.
- CORS·XSRF 검사를 통째로 해제해 연동 문제를 해결하지 마세요. 접속 origin과 프록시 헤더의 신뢰 범위를 정확히 설정하세요.
- 세션 쿠키의 HttpOnly·SameSite 정책과 HTTPS 사용 시 Secure 설정을 일관되게 적용하세요. HTTPS 또는 앞단 TLS 종료 구성을 문서화하고 HTTP 운영 시의 전송 보호 범위를 명시하세요.
- 운영 DB, 계정 명단, 제출물, 임시비밀번호 결과물, 비밀값, 로그, 가상환경, 부하 테스트용 대용량 파일을 Git 추적에서 제외하세요.

## 12. 로컬 실행과 제공 파일

운영자가 일상적으로 복잡한 명령을 입력하지 않도록 Windows용 진입점을 제공하세요. 아래 파일명은 기본안이며 더 명확한 구성이 필요하면 일관되게 조정하세요.

- `setup.bat`: 지원 Python 확인, 프로젝트 내부 `.venv` 생성, 고정된 의존성 설치.
- `manage.bat`: 인스턴스 생성, 설정, 시작, 상태 확인, 중지 기능의 진입점.
- 인스턴스를 지정해 실행·중지할 수 있는 CLI. 외부 접속 포트를 실행 옵션 또는 인스턴스 설정으로 변경 가능.
- 두 인스턴스 설정 예제와 사용자 등록용 `users_template.xlsx`.
- `README.md`: 빠른 시작, 기능 범위, 실행 예시.
- `docs/requirements.md`: 이번 요구사항과 기본 가정.
- `docs/architecture.md`: 서비스 구성, 인증 연결, 업로드 프로토콜, 상태 전이, 장애 복구, 용량 계산.
- `docs/admin-guide.md`: 인스턴스 관리, 명단 등록, 비밀번호 초기화, 제출물 확인, 용량 관리, 정상 종료 후 백업·복원.
- `docs/user-guide.md`: 최초 로그인, 비밀번호 변경, 과제 제출, 진행률 해석, 재시도.
- `docs/test-report.md`: 실제 실행 결과와 미실행 항목.
- 재현 가능한 의존성 정의·잠금 파일, 테스트 코드, 대용량 검증 도구.

설치는 네트워크를 사용할 수 있으나 설치 완료 후의 계정 인증과 과제 제출은 외부 클라우드 서비스나 CDN을 필요로 하지 않도록 하세요. 인증과 파일 저장은 모두 해당 PC에서 처리하세요.

첫 버전의 필수 배포 형태는 Python 소스와 BAT 실행 도구입니다. EXE 패키징을 필수 조건으로 추가해 핵심 구현을 지연시키지 마세요. 실행 파일로 배포할 때 고려할 내용은 문서에 정리할 수 있습니다.

## 13. 검증과 완료 기준

실패 시나리오를 재현하는 자동 테스트와 실제 브라우저·네트워크 검증을 구분하세요. 작은 파일로 로직이 통과한 것과 실제 2GiB 전송이 검증된 것은 별도로 보고하세요.

| ID | 검증 항목 | 통과 기준 |
|---|---|---|
| A01 | 명단 등록·재등록 | ID 앞자리 0 보존, 중복·누락 오류 안내, 재등록 후 기존 비밀번호·제출 이력 보존 |
| A02 | 최초 비밀번호 변경 | 변경 전 UI와 API에서 과제 접근 불가, 변경 후 정상 로그인·제출 가능 |
| A03 | 관리자 비밀번호 초기화 | 기존 세션과 업로드 권한 무효화, 재변경 전 청크 수신·제출 확정 차단 |
| A04 | 사용자 권한 분리 | 다른 사용자 제출·업로드 ID를 사용해도 조회·청크 전송·확정·다운로드 불가 |
| U01 | 실제 대용량 파일 | 정확히 2GiB인 파일의 실제 전송, 원본·저장본 크기와 해시 일치, 재시작 후 보존 |
| U02 | 파일 크기 경계 | 제한과 같은 크기는 허용, 1바이트 초과는 거절. 신고 크기 위조와 초과 청크도 차단 |
| U03 | **대용량 동시 업로드** | 기본 4개 파일을 동시에 실제 전송. 별도 사용자 및 동일 사용자의 여러 탭을 검증하고 혼합·손상·중복 집계 없음 |
| U04 | **전송 중 연결 종료** | 파일 중간과 청크 중간 연결 종료 후 서버 확정 offset에서 재개, 원본 해시 일치 |
| U05 | 재시도·응답 유실 | 같은 청크 반복, 완료 응답 유실 후 재확정에도 제출·파일·사용량 중복 없음 |
| U06 | 전송률과 완료 상태 | 100% 전송 후 검증·저장 단계 표시, 최종 커밋 전 성공 표시 없음 |
| U07 | 여러 파일 제출 | 일부 파일 실패 시 묶음 미완료, 재개 후 모든 파일 완료 시 제출자 집계 반영 |
| U08 | 서버 강제 종료·복구 | 청크 기록 중, 파일 이동 후 DB 커밋 전, 커밋 후 응답 전에 종료해 각각 복구·재시도 가능 |
| Q01 | 사용자 누적 한도 | 여러 과제·재제출·동시 탭의 완료 사용량과 예약 용량을 합산하고 한도 초과 방지 |
| Q02 | **디스크 부족** | 시작 전, 전송 도중, 최종 저장·DB 갱신 시 부족을 재현. 거짓 성공·파일 손상·서버 전체 종료 없음 |
| Q03 | 취소·만료 | 임시 파일과 예약 용량 정리, 활성 업로드와 완료 파일은 보존 |
| I01 | **인스턴스 간 데이터 분리** | 같은 ID를 두 인스턴스에 등록한 뒤 계정·세션·비밀번호·제출물·용량 집계가 독립적으로 동작 |
| I02 | 같은 호스트의 쿠키 분리 | 같은 브라우저로 두 포트에 로그인해도 세션이 섞이지 않으며 다른 인스턴스 토큰 재사용 불가 |
| I03 | 실행·중지 분리 | 한 인스턴스 중지가 다른 인스턴스와 무관한 프로세스에 영향 없음, 포트·저장 루트 충돌 안내 |
| I04 | 동일 볼륨 공간 경합 | 다른 인스턴스 또는 외부 쓰기로 공간이 줄어도 오류를 처리하고 양쪽 완료 제출물 보존 |
| M01 | 관리자 현황 | 대상자·제출자·미제출자·재제출 수치가 정의와 일치, 파일 목록·시각·내보내기 일치 |
| S01 | 파일명 처리 | 한글·공백·동일 이름·예약 이름·경로 조작에도 안전하게 저장하고 원본 이름 추적 가능 |
| E01 | Windows 실행과 브라우저 | BAT 실행부터 실제 접속 주소·WebSocket·인증·업로드·다운로드·종료까지 정상 동작 |

일상적인 자동 테스트는 작게 조정한 제한값과 실패 주입으로 경계·권한·복구 로직을 검증하세요. 디스크 부족 테스트는 격리된 임시 저장소 또는 실패 주입을 사용하고 운영 데이터가 있는 디스크를 실제로 가득 채우지 마세요.

실제 대용량 검증은 별도 실행 가능한 스크립트로 제공하세요. 예를 들어 기본 `4명 × 2GiB` 전송을 지원하고 사용자 수·파일 크기·대상 인스턴스를 인자로 변경할 수 있게 하세요. 파일 생성과 해시 계산도 스트리밍으로 하고, 전체 파일을 메모리에 생성하지 마세요. 테스트가 만든 데이터만 정리하세요.

대용량 검증 결과에는 파일 크기, 동시 전송 수, 수행 환경, 시간, 성공·실패 수, 해시 일치 여부, 서버 프로세스 트리 전체의 최고 RSS와 실행 전 기준 메모리, 임시 디스크 사용량을 남기세요. 메모리 사용량이 전송한 파일 크기 합계만큼 증가하지 않는지 비교하세요. 프록시와 브라우저 업로더까지 포함한 실제 경로도 확인하세요. 사용 환경을 보지 않고 임의의 전송 속도나 최대 수용 인원을 보장하지 마세요.

현재 환경에서 Windows 또는 실제 2GiB·동시 전송을 실행할 수 없다면, 재현 명령과 검증 도구를 완성하고 해당 항목을 **미검증**으로 표시하세요. 작은 샘플, 모의 응답, 코드 검토만으로 대용량·Windows 검증 완료라고 보고하지 마세요.

## 14. 진행 방식과 최종 보고

다음 순서로 진행하되, 계획이나 문서 작성 단계에서 멈추지 말고 구현과 검증까지 이어가세요.

1. 저장소와 실행 환경을 확인하고 짧은 구현 계획을 제시합니다.
2. 위 기본 가정과 핵심 설계 결정을 요구사항·설계 문서에 기록합니다.
3. 단일 포트에서 실제 로그인과 브라우저→디스크 청크 전송이 동작하는 최소 경로를 먼저 만듭니다.
4. 계정 등록·비밀번호 변경·초기화, 과제·제출, 용량 예약, 관리자 현황, 여러 인스턴스 실행을 완성합니다.
5. 장애 복구, 권한, 동시성, 경계값 테스트를 실행하고 실제 확인된 문제를 수정합니다.
6. 실행 도구, 템플릿, 문서, 대용량 검증 스크립트를 마무리합니다.

단순 화면 목업, 가짜 진행률, 메모리 전체 적재 방식, 핵심 기능을 남겨 둔 TODO만으로 완료 처리하지 마세요. 불확실한 세부 선택은 이 문서의 기본값으로 진행하고 변경 가능한 설정으로 남기세요. 요구사항을 바꾸어야 할 구체적 장애가 있으면 근거와 영향을 설명하세요.

최종 보고에는 다음을 포함하세요.

- 구현한 기능과 주요 파일.
- 설치와 최초 실행 명령, 두 인스턴스 동시 실행 예시.
- 관리자 최초 설정, 명단 등록, 수강생 최초 로그인 방법.
- 저장 위치와 정상 종료 후 백업·복원 절차.
- 각 완료 기준의 통과·실패·미검증 상태와 실제 테스트 명령.
- 남은 제약, 적용한 기본 가정, 사용자가 조정할 설정.

## 15. 구현 시 확인할 공식 문서

아래는 기술 선택을 위한 참고 자료입니다. 요구사항과 기본값은 이 프롬프트에서 정한 설계안이며 라이브러리가 자동으로 제공한다고 가정하지 마세요. 개발 환경에서 사용할 버전의 공식 문서를 확인하고 검증한 버전으로 의존성을 고정하세요.

- [Streamlit 파일 업로더](https://docs.streamlit.io/develop/api-reference/widgets/st.file_uploader): 기본 업로드 제한과 반환 형식.
- [Streamlit 업로드 데이터 저장 위치](https://docs.streamlit.io/knowledge-base/using-streamlit/where-file-uploader-store-when-deleted): 기본 업로더가 업로드 데이터를 메모리에 보관하는 특성.
- [Streamlit 설정 옵션](https://docs.streamlit.io/develop/concepts/configuration/options): 인스턴스 실행 옵션과 포트 지정.
- [FastAPI 파일 요청](https://fastapi.tiangolo.com/tutorial/request-files/): `bytes` 전체 적재와 `UploadFile` 임시 파일 처리의 차이. 이어 올리기·진행률·멱등성과 완료 처리는 별도 구현 대상.
- [RFC 6265, 8.5절](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5): 쿠키는 포트별 격리를 제공하지 않으므로 인스턴스 인증 구성을 별도로 설계해야 함.
- [OWASP 비밀번호 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): 비밀번호 해시 알고리즘 선택과 안전한 저장 방식.
