# 구조와 데이터 흐름

## 로컬 서버 관리창

`start.bat`가 Python/Tk와 설치 상태를 확인하고 `server_manager.py`의 로컬 창을 엽니다. 이 창의 과정 생성·설정·점검은 `management.py`, 실제 서버 프로세스의 시작·중지는 기존 `launcher.py`를 사용합니다. 서버 제어를 위한 외부 HTTP 엔드포인트는 추가하지 않습니다. 작업 스레드에서 시작·중지·저장을 수행하고 Tk 메인 스레드가 결과 큐를 반영하여 창의 응답을 유지합니다. 관리창과 서버 supervisor의 수명은 분리되며, 창을 닫아도 서버는 유지됩니다. 과정 설정은 기존 JSON을 그대로 사용하고, 외부 설정 파일을 연결한 경로 목록만 로컬 카탈로그에 별도 보관합니다.

## 단일 접속 주소

```text
수강생/관리자 Chrome·Edge
        │ HTTP(S) / WebSocket :외부포트
        ▼
     Caddy 게이트웨이
        ├─ /api/* /upload /upload-static/* → FastAPI (127.0.0.1:자동포트)
        └─ /ui/{instance_id}/ + WebSocket → Streamlit (127.0.0.1:자동포트)
                                               │ 로컬 API 요청
                          FastAPI 인증·업로드·관리 API
                                  ├─ SQLite WAL
                                  └─ 같은 저장 볼륨의 임시·완료 파일
```

Streamlit을 ASGI 앱처럼 mount하지 않습니다. 실행 도구가 프로세스와 Caddy 구성을 관리합니다. Caddy는 HTTP·WebSocket을 중계하고 파일 요청을 전체 버퍼링하지 않습니다. 여러 인스턴스의 외부 포트·저장 루트·DB·비밀값·프로세스는 서로 독립적입니다. 정규화한 저장 경로에 실행 잠금을 사용하며 실행 실패 시 해당 실행에서 만든 프로세스만 정리합니다.

## 인증 연결

API의 불투명 bearer 세션은 해당 인스턴스 비밀값에 연결된 해시 형태로 DB에 저장합니다. 비밀번호는 Argon2id로 저장합니다. Streamlit 인증 상태는 개인 `session_state`에 보관합니다. 파일 제출 버튼은 현재 세션과 선택한 과제를 같은 origin의 `POST /upload` 본문으로 전달합니다. 서버가 로그인 상태를 확인한 뒤 제출 화면을 반환하며, 브라우저는 인증 데이터를 메모리에 읽고 DOM의 초기화 데이터를 제거합니다. 연결 코드 발급·교환 단계는 없습니다. 로그인 토큰을 URL, `localStorage`, `sessionStorage`, 일반 로그에 넣지 않습니다. 제출 주소로 직접 접속하면 ID·비밀번호로 로그인합니다.

비밀번호는 8~128자입니다. 최초 발급 및 초기화 임시비밀번호는 영문·숫자 8자리(UTF-8 8바이트)입니다. 명단 등록 시 공통값을 지정할 수 있으며 해당 명단의 신규 계정에만 적용합니다. 기존 계정은 보존하고 추가 등록 때 공통값을 다시 지정합니다. 공통값도 사용자별로 별도의 salt를 사용해 해시하고 평문 설정으로 저장하지 않습니다. 첫 로그인 후 개인 비밀번호 변경은 계속 필요합니다.

브라우저 API 인증에 포트 공유 쿠키를 사용하지 않으므로 같은 호스트의 두 포트를 쿠키 격리 경계로 가정하지 않습니다. Streamlit의 XSRF 쿠키 경로를 `/ui/{instance_id}/`로 한정하고 SameSite=Lax 및 HTTPS 시 Secure를 적용합니다. XSRF 쿠키는 브라우저 JavaScript가 읽는 용도이므로 HttpOnly 세션 쿠키로 사용하지 않습니다. Streamlit 자체 XSRF/WebSocket 보호는 유지합니다. API 요청마다 인스턴스·세션·계정 활성 상태·필수 비밀번호 변경·작업 소유권을 검사합니다. 초기화·비활성화는 기존 세션과 업로드 접근을 즉시 무효화합니다. 비밀번호 변경 후 재로그인해야 합니다. 일회용 다운로드 권한도 URL 대신 POST 본문으로 전달하며 원래 세션의 유효성을 확인합니다.

## 업로드 프로토콜

1. 파일 선택 후 파일명·크기·합계·제한을 표시합니다. 사용자가 제출 시작을 누르면 제한된 청크로 파일 해시를 계산합니다.
2. `POST /api/uploads`가 과제, 클라이언트 요청 UUID, 고정 파일 목록, 크기, SHA-256을 검증합니다. 사용자 한도와 디스크 여유를 확인하고 DB에서 합계 용량을 한 번 예약합니다.
3. `PATCH /api/uploads/{id}/files/{file_id}?offset=N`은 요청 스트림을 제한해서 읽습니다. `X-Chunk-SHA256`, offset, 최대 청크, 실제 수신량, 총 크기를 검증합니다. 파일 기록·동기화 후 확정 offset을 커밋합니다. 전체 파일 전송 중 DB 쓰기 트랜잭션을 유지하지 않습니다.
4. 연결이 끊기거나 응답이 유실되면 상태 조회에서 확정 offset을 확인합니다. 같은 확정 청크의 동일 재전송은 성공하고 다른 내용·잘못된 offset은 거절합니다. 새로고침 후 파일을 재선택하면 전체 SHA-256을 비교해 잘못된 파일 연결을 막습니다.
5. 완료 요청은 모든 파일의 실제 크기와 SHA-256을 제한된 버퍼로 확인하고 최종 위치로 이동합니다. 파일 메타데이터·시각·번호·완료 상태·용량 전환을 DB에 커밋한 후 `completed`를 반환합니다.
6. 클라이언트는 전송 100%를 성공으로 취급하지 않고 검증·저장 상태를 보여 줍니다. 완료 응답 재요청은 기존 결과를 반환합니다.

파일 읽기·쓰기·해시는 작업 스레드에서 처리하여 긴 파일 I/O로 API 이벤트 루프를 막지 않습니다. 브라우저는 파일 하나 전체를 단일 ArrayBuffer로 만들지 않습니다. 다운로드도 제한된 버퍼로 스트리밍합니다.

## 상태·복구 정책

| 상태 | 의미와 가능한 다음 단계 |
| --- | --- |
| `uploading` | 확정 offset까지 수신됨. 계속 전송, 검증, 취소 가능 |
| `paused` | 재시작·연결 문제 뒤 재개 가능한 미완료. 동일 파일 확인 후 uploading |
| `verifying` | 고정 목록의 모든 파일 크기·해시 확인. 성공 시 finalizing |
| `finalizing` | 최종 파일 이동·완료 DB 확정 진행. 재시작 시 파일·DB 대조 후 재검증 |
| `completed` | 모든 파일과 DB 확정. 다운로드 가능, 완료 재요청은 동일 결과 |
| `failed` | 검증·저장 실패. 성공 집계 제외; 정리로 예약·임시 데이터 해제 |
| `cancelled` | 사용자가 취소함. 미완료 파일·예약 정리, 완료로 전환 불가 |
| `expired` | 마지막 활동 기준 보관 시간 초과. 활동 중인 청크와 잠금 조정 후 정리 |

청크 파일 기록이 DB offset보다 앞서 있으면 재시작 시 마지막 확정 offset으로 잘라 재개합니다. 파일이 이동됐지만 완료 DB 커밋이 안 된 경우 원래 임시 경로와 최종 경로를 대조해 파일을 찾고 재검증합니다. DB 완료 뒤 응답이 유실되어도 동일 업로드 완료 재요청으로 기존 결과를 돌려줍니다. 미확정 파일은 목록·다운로드에 노출하지 않습니다.

파일은 flush·fsync 후 같은 볼륨에서 이름을 바꾸고 SQLite의 동기화 설정을 사용합니다. POSIX는 디렉터리 fsync도 수행하며 Windows에서는 파일 fsync를 수행합니다. 지원 범위는 애플리케이션 프로세스 종료·재시작에 대한 복구입니다. 갑작스러운 전원 차단, 저장장치의 쓰기 캐시 거짓 응답, 하드웨어 장애에 대한 완전한 보장은 하지 않습니다. 다운로드 시 완료 파일의 외부 삭제·크기 변경을 검출하고 복원 요청 오류를 표시합니다. 같은 크기의 외부 내용 변경은 자동 검출하지 않으며 보관된 SHA-256으로 별도 비교해야 합니다. 저장 루트를 실행 중에 수동 편집하지 마세요.

## 용량 계산

사용자 예약 조건은 `보존 중인 완료 파일 총합 + 기존 예약 + 새 제출 합계 <= 사용자 한도`입니다. 서로 다른 과제와 모든 재제출을 포함하며 같은 사용자 동시 탭 예약은 SQLite 쓰기 트랜잭션으로 직렬화합니다.

디스크는 실제 볼륨의 사용 가능 공간에서 아직 쓰지 않은 예약량과 최소 여유를 고려합니다. 이미 기록한 임시 바이트는 OS 여유 공간에 반영되므로 다시 차감하지 않습니다. 임시 파일과 완료 파일은 같은 볼륨에서 이동하여 별도 전체 사본을 만들지 않습니다. 시작·청크 수신·최종 확정에 디스크 여유를 재검사하고 OS 공간 부족 쓰기 오류도 포착합니다. 다른 인스턴스·외부 프로그램의 공간 소비는 인스턴스 DB 예약만으로 막을 수 없습니다.

완료 시 예약이 사용량으로 전환되고 취소·만료·실패 정리 시 예약이 해제됩니다. 관리자는 완료 사용량, 예약, 실제 임시 파일 크기, 볼륨 잔여 공간을 구분해서 봅니다.

## 파일명·관리 기록·내보내기

실제 저장 이름은 서버 내부 UUID입니다. 표시 ID와 원본 이름은 DB 메타데이터이며 경로로 조합하지 않습니다. 경로 조작, Windows 예약 이름·ADS 등을 검증하고 한글·공백·같은 이름을 안전하게 다룹니다. 화면은 사용자 입력을 이스케이프하고 CSV 수식 시작 문자는 텍스트로 내보냅니다. 인증 없는 제출 파일 정적 경로는 없습니다.

계정 초기화·활성화 변경·과제 접수 변경·명단 반영은 관리자 ID와 UTC 시각을 기록합니다. 비밀번호·토큰은 관리 로그와 운영 DB 평문에 남기지 않습니다. 임시비밀번호는 등록/초기화 결과에만 한 번 표시합니다.

## 공식 문서 확인

기술 선택 시 아래 공식 문서를 확인했습니다. 이어 올리기·권한·용량 예약·묶음 완료는 해당 라이브러리가 자동 제공하는 기능으로 가정하지 않고 애플리케이션에서 구현·검증합니다. 실제 설치 버전은 `requirements.lock`으로 고정합니다.

- [Streamlit 파일 업로더](https://docs.streamlit.io/develop/api-reference/widgets/st.file_uploader), [업로드 파일의 메모리 보관](https://docs.streamlit.io/knowledge-base/using-streamlit/where-file-uploader-store-when-deleted): 작은 명단 수신과 대용량 제출 경로를 구분하는 근거.
- [Streamlit 설정 옵션](https://docs.streamlit.io/develop/concepts/configuration/options): 내부 바인딩, 포트, base URL, XSRF/WebSocket 설정.
- [FastAPI 파일 요청](https://fastapi.tiangolo.com/tutorial/request-files/), [Starlette 요청 스트림](https://www.starlette.dev/requests/): 전체 bytes 수신과 스트림 처리의 차이.
- [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy): HTTP·WebSocket 게이트웨이 설정과 스트리밍.
- [RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5): 브라우저 쿠키의 포트 격리를 가정하지 않는 설계.
- [OWASP 비밀번호 저장](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html): Argon2id 비밀번호 해시.
- [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous): WAL과 동기화 내구성 범위.
